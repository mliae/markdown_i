## 2026-10-11：上传存储三后端改造 + 部署上线 + 域名移交宝塔管理

### 一、背景

原 Node 版后台上传存储只有 `r2 / b2` 两个选项，且其中的 `r2` 实际是写本地磁盘
（Workers 语义迁移过来的历史包袱），容易误解。

需求（用户原话）：

> 后台的上传存储应该是本地、R2、B2，R2 和 B2 一样——选择 R2 时出现设置栏目。

### 二、最终设计：key 前缀决定物理后端

`storage_mode` 三选一（默认 `local`）：

| 模式 | 新上传位置 | 对象 key 前缀 |
|---|---|---|
| local | 本地磁盘 `data/media/`，`/media/` 输出 | 无 |
| r2 | Cloudflare R2（S3 API） | `r2/` |
| b2 | Backblaze B2（S3 API） | `b2/` |

关键点：**读写/删除/代理全部按 key 前缀路由，与当前模式无关**，所以历史文件
（老本地文件无前缀、B2 文件带 `b2/`）在任何模式下都永久可达、可删，切换零迁移成本。

### 四、过程中修掉的两个真实 bug

1. **Node 下对象存储上传必 500**：undici 用 `ReadableStream` 作为 fetch body 时必须
   `duplex:"half"`（Workers 不需要）。表现为上传 500
   `RequestInit: duplex option is required when sending a body.`。
   修法：`s3Fetch` 检测 Node 运行时且 body 为流时自动加 `duplex:"half"`。
   `node-entry.ts` 的 `withRealIp` 重包装 Request 处同理（原有）。
2. **本地批量删除静默失败**：`deleteObjects` 对本地 key 调 `r2.delete(keys[])`，
   而 DiskR2 只实现了单参 `delete(key)`，数组会被当成路径片段，删动态/图集时
   本地媒体文件残留。修法：DiskR2 兼容数组重载；storage 层本地 key 也逐个删除双保险。
